# JDK Common Validation

Cross-cutting validation, formatting and security-sensitive input checks
that must have one authoritative implementation instead of being
reimplemented per business module (Sales, Finance, etc.).

## 1. User / Company Email

- Valid email format.
- Only the organisation's configured company domain is allowed.
- Domain is configuration, not hard-coded.
- Server validates authoritatively.
- Duplicate user email prevented within the organisation.
- Normalise email consistently.

## 2. Date Validation

Standard user-facing format: `DD/MM/YYYY`.

Common rules: valid calendar date; no ambiguous date formats; consistent
date picker/input; internal storage remains machine-readable.

### Date relationships

Common validation must support:

- From Date ≤ Valid Till Date
- From Date ≤ To Date
- Start date cannot be after end date.
- Where applicable, dates cannot be in the past/future according to the
  business rule.
- Same-day validity must be handled correctly.

Example: `From: 22/09/2026`, `Valid Till: 22/09/2026` → valid.
`From: 23/09/2026`, `Valid Till: 22/09/2026` → invalid.

The actual business module determines whether past/future dates are
allowed; the common validator provides the reusable date comparison
mechanism.

## 3. Date & Time

Display: `DD/MM/YYYY HH:mm`. Use the established JDK/Kuwait timezone
consistently. Do not allow individual modules to implement their own
timezone conversion.

## 4. Currency — KWD

JDK standard currency: KWD. Display consistently, e.g. `KWD 125.500`.

Rules: central KWD configuration; correct KWD decimal precision;
decimal arithmetic; consistent rounding; server recalculates
authoritative amounts; database stores numeric values, not formatted
currency strings.

## 5. QR Code Validation & Branding

For QR codes generated by JDK, source/domain validation must be
centralized:

- Validate the URL before generating the QR.
- Only approved JDK/company domains may be used where the QR represents
  a JDK-controlled resource.
- Do not allow arbitrary external URLs to be silently presented as
  official JDK/company QR codes.
- Domain/allowed-origin configuration must be centralized.
- HTTPS required for production QR destinations.
- QR content must correspond to the intended record/action.

Branding: use standard JDK/company branding; consistent logo treatment,
sizing and placement where branding is supported; do not allow
individual modules to invent QR branding; QR must remain reliably
scannable — branding must not compromise the encoded data.

Example: a payment QR on an invoice should point to the approved
payment-link domain, not an arbitrary URL supplied by the browser.

## 6. Common Validation Types

Centralize reusable validation for: required fields, email, company
email domain, phone, date, date ranges, date/time, numbers,
currency/decimal, percentage, min/max values, string length, allowed
values, unique values, IDs/references, file type/size, URLs/domains,
QR source/domain, password rules, cross-field relationships.

### Important boundary

Common validation provides the mechanism. The module provides the
business rule.

Example: Common: `dateA must not be after dateB`. Sales: `Quotation
Valid Till must not exceed the permitted quotation validity period.`

This prevents the common layer from becoming a business-rule engine.

## ID formats

## Core principle

All reusable validation, formatting constraints and security-sensitive
input checks should have one authoritative implementation. Frontend
validation improves usability; server-side validation enforces
correctness. Business modules supply business-specific rules.
